- 2026-08-16: v2.43.1 — keyboard no longer covers the focused field on the web/PWA build (Scott reported it on New Entry → Notes, with a screenshot). Root cause: react-native-web does NOT implement the keyboard APIs the native side uses — its `Keyboard` module is a stub whose `addListener` never fires and whose `isVisible()` always returns false, and `KeyboardAvoidingView` renders a plain `View` with an empty `onKeyboardChange`. So on the PWA *nothing* avoided the keyboard, including the four auth screens that look protected because they wrap themselves in a KeyboardAvoidingView. Fix: `lib/useKeyboardInset.ts` derives the covered height from the VisualViewport API (layout viewport minus `visualViewport.height + offsetTop`; ignores <80px so URL-bar chrome isn't mistaken for a keyboard, caps at 70%), plus `useScrollFocusedFieldIntoView` which scrolls the nearest scrollable ancestor by an exact delta — `scrollIntoView({block:'center'})` was tried first and is WRONG here because it centres within the container, whose centre is roughly where the keyboard starts (measured: field landed 19px under the keyboard line). New `components/ui/KeyboardAwareScrollView.tsx` wraps ScrollView, appends a spacer of exactly the covered height (a trailing spacer, NOT `paddingBottom` on contentContainerStyle — the longhand would override the `padding` shorthand these screens use and silently drop their side/top padding), and sets `automaticallyAdjustKeyboardInsets` on iOS only. Native is deliberately untouched: iOS handles it via that prop, Android via adjustResize, so the hook returns 0 there and nothing double-counts. Applied to NewCalling, CallingDetail (+ decline/edit bottom sheets, lifted by `paddingBottom: inset`), HighCouncil, SlackSettings, SuggestionFAB, and all five auth screens.
